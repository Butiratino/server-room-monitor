# Техническая записка: монитор температуры серверной и Zabbix

**Назначение:** справочник оператора и инструкция по развёртыванию проекта на другой Windows-машине.  
**Производственная прошивка:** `main/temperature_monitor.c`.  
**Среда, зафиксированная проектом:** ESP-IDF 6.1.0, target `esp32s3`, компонент OLED `chill-sam/ssd1306` 1.1.2.

## 1. Как читать сведения о проверках

В тексте разделены три уровня утверждений:

- **Подтверждено на текущем устройстве/в тестах** — результаты, полученные ранее на физической плате или Unity-тестами.
- **Следует из исходников/конфигурации** — поведение, просмотренное в коде, но не обязательно проверенное нажатием кнопки или реальным отказом сети.
- **Не проверено физически** — явно перечислено в разделе [Проверено и не проверено](#14-проверено-и-не-проверено).

Успешный ответ Zabbix Sender означает принятие пакета на уровне протокола и проверку ожидаемых полей ответа прошивкой. Он сам по себе не доказывает, что оператор открыл веб-интерфейс, что нужный элемент отображается в **Latest data** или что настройка визуально проверена.

## 2. Плата и подключение BMP280

### Плата

Используется Heltec **WiFi LoRa 32 V4**, маркировка платы **HTIT-WB32LAF V4.3**, модуль ESP32-S3R2. По сведениям, ранее проверенным на плате, установлены Flash 16 МБ и PSRAM 2 МБ. Таблица разделов проекта стандартная, раздел приложения — 1 МБ; размер Flash не увеличивает его автоматически. Радиотракт LoRa этому приложению не нужен.

Источники платы: [официальная схема V4.3](https://resource.heltec.cn/download/WiFi_LoRa_32_V4/Schematic/HTIT-WB32LAF_V4.3.pdf), [pin map V4](https://resource.heltec.cn/download/WiFi_LoRa_32_V4/Pinmap/V4_pinmap.png), [документация Heltec](https://docs.heltec.org/en/node/esp32/wifi_lora_32/index.html). На pin map плата показана OLED к наблюдателю и USB-разъёмом вниз; J3 находится слева. Перед подключением сверить маркировку именно своей ревизии и выводы конкретного модуля BMP280.

### Соединения датчика

Подключать и менять проводку только при отключённых USB и аккумуляторе. На ESP32-S3 нельзя подавать 5 В на GPIO.

| Модуль BMP280 | Heltec V4.3 | Примечание |
|---|---|---|
| `VCC` / `VIN` | `3V3`, J3 контакт 2 или 3 | Использовать питание 3,3 В |
| `GND` | `GND`, J3 контакт 1 | Общая земля |
| `SDA` / `SDI` | GPIO4, J3 контакт 15 | Шина датчика I2C №1 |
| `SCL` / `SCK` | GPIO6, J3 контакт 17 | Шина датчика I2C №1 |
| `CS` / `CSB` (если выведен) | 3V3 | Выбрать I2C у шестиконтактного модуля |
| `SDO` (если выведен) | GND | Адрес 0x76; при подключении к 3V3 был бы 0x77 |

Распиновка J3 выше — выбранная в проекте точка подключения датчика, а не отдельная заводская инструкция Heltec для BMP280. Производственная прошивка обращается **только к BMP280 по адресу 0x76** и не ищет датчик по альтернативному адресу. Для четырёхконтактных платок CSB/SDO могут быть уже соединены на модуле: проверить схему модуля и наличие подтяжек SDA/SCL к 3,3 В. OLED использует отдельную шину: SDA GPIO17, SCL GPIO18, RESET GPIO21; питание OLED включается GPIO36 уровнем LOW. Датчик не подключать к этим OLED-контактам.

## 4. Запуск и потоки данных

### Старт приложения

`app_main()` производственной прошивки выполняет последовательность:

1. Устанавливает драйвер USB Serial/JTAG (TX-буфер 1024 байта), включает питание OLED через GPIO36.
2. Создаёт OLED I2C-шину №0 на GPIO17/18, дисплей 128×64 по адресу 0x3C с RESET GPIO21.
3. Создаёт I2C-шину №1 на GPIO4/6 и устройство BMP280 по адресу 0x76, частота I2C 100 кГц; посылает программный reset BMP280.
4. Запускает `wifi_manager_start()`. Если он запустился, создаёт отдельную задачу `zabbix_sender_start()`.
5. В основном цикле раз в секунду читает датчик (если его инициализация не завершилась ошибкой), публикует последний снимок для отправителя, обновляет OLED и выводит строку JSON через USB Serial/JTAG.

Ошибки инициализации USB/OLED, обёрнутые в `ESP_ERROR_CHECK`, приводят к аварийному завершению приложения при ошибке. Ошибка начальной настройки I2C датчика сохраняется как `init_error`: приложение продолжает выдавать диагностические отчёты, но повторно не создаёт шину/устройство и не пытается восстановить датчик без перезапуска. Ошибка старта Wi-Fi не останавливает основной цикл измерений; при ошибке `wifi_manager_start()` задача отправителя не создаётся.

### Разделение задач

- **Основная задача** — измерение, публикация актуального снимка, OLED и USB JSON с периодом около 1 секунды.
- **Wi-Fi manager** — состояние STA/AP, веб-страница настройки, PRG и повторные подключения.
- **Zabbix sender** — отдельная задача; работает только при состоянии Wi-Fi `online`.

В буфере находится только последний снимок. Очереди истории и повторной отправки пропущенных измерений нет: после восстановления связи отправляется актуальное измерение, а не серия накопленных старых значений. Сетевой sender имеет отдельные таймауты I/O; вызов DNS `getaddrinfo()` выполняется синхронно и не имеет отдельного таймаута, заданного в проекте.

### USB-отчёты и OLED

При успешном измерении JSON типа `measurement` содержит `state=ok`, модель `BMP280`, адрес `118` (десятичное представление 0x76), сырые байты/коды ADC, байт `status`, компенсированные `temperature_c` и `pressure_pa`, коэффициенты `t1/t2/t3`, `uptime_ms`, `wifi_state`, `wifi_error`, `wifi_reason_code`, `zabbix_send_state`, `zabbix_stage`, `zabbix_error` и `error=ESP_OK`.

При ошибке датчика компенсированные поля равны `null`. Если сырые регистры уже успели прочитаться, отчёт сохраняет raw-байты, raw-коды и статус; при ранней ошибке I2C они равны `null`. Поле `wifi_error` — строковая категория Wi-Fi, а не `esp_err_to_name()`. Поле `zabbix_error` содержит имя ESP error для последней ошибки отправителя. Периодический JSON не включает SSID или пароли. Отдельное однократное USB-сообщение типа `wifi_setup` при запуске setup AP содержит временные данные подключения к AP — его нельзя публиковать.

На OLED отображаются температура, давление и сокращённые статусы. В режиме настройки отображаются SSID setup AP, его пароль, URL портала и диагностические строки. В сетевых ошибках OLED показывает короткий текст, USB-отчёт сохраняет машинно-читаемые поля.

## 5. BMP280: измерение, компенсация и ошибки

Функция `bmp280_read_temperature()` на каждом чтении:

1. Проверяет chip ID `0xD0` (ожидается `0x58`) и читает калибровочные коэффициенты из `0x88..0x9F`; EEPROM датчика не перепрограммируется.
2. Переводит датчик в sleep, ждёт сброса busy/NVM update, отключает фильтр (`0xF5 = 0`), затем начинает forced-mode измерение с oversampling температуры и давления ×1 (`0xF4 = 0x25`).
3. После защитной паузы опрашивает busy/NVM status (маска `0x09`) с ограничением ожидания 100 мс, читает статус `0xF3` и шесть байтов `0xF7..0xFC`.
4. Рассчитывает температуру и давление double-precision формулами из раздела 3.11.3 даташита Bosch. Сырые данные сохраняются до компенсации.
5. Возвращает `ESP_ERR_INVALID_RESPONSE`, если ID не BMP280, коэффициенты/ADC недостоверны, температура вне диапазона −40…85 °C или давление вне 30 000…110 000 Па. При ошибке I2C возвращается исходный `esp_err_t`.

Поле `raw_bytes` в отчёте — двенадцать заглавных hex-символов в порядке регистров F7..FC: три байта давления, затем три байта температуры. `raw_pressure` и `raw_temperature` — 20-битные значения, собранные из соответствующих групп. `status` — значение регистра 0xF3, не строковая метка «успешно».

При невалидных данных sender передаёт `sensor.status=error` и не отправляет числовые температуру/давление. При валидном чтении отправляет оба числа и `sensor.status=ok`. Прошивка не измеряет влажность; BME280 в диагностическом `sensor_probe.c` распознаётся, но production-драйвер его не поддерживает.

## 6. Wi-Fi: первый запуск, сохранение и восстановление

### Первая настройка и форма

Если в NVS нет валидного сохранённого профиля, прошивка стартует с setup AP и HTTP-страницей `http://192.168.4.1`. SSID начинается с `RoomMonitor-` и завершается шестью hex-символами MAC; временный случайный пароль формируется из 12 символов. AP использует WPA2-PSK, канал 1, допускает до двух клиентов. Captive portal нет: URL следует открыть вручную.

Форма содержит SSID, пароль Wi-Fi, адрес Zabbix и порт. Валидация исходников:

| Поле | Ограничения |
|---|---|
| SSID | Обязателен, 1–32 байта после декодирования формы |
| Пароль Wi-Fi | Может быть пустым (открытая сеть); иначе 8–63 символа либо ровно 64 hex-символа |
| Адрес Zabbix | Обязателен, 1–253 ASCII символа из `A–Z`, `a–z`, цифр, `.` и `-`; точка не может быть первой/последней или идти подряд |
| Порт | Если не указан — 10051; иначе только цифры, диапазон 1–65535 |
| HTTP body | Непустой, не более 1024 байт; form-urlencoded `+`/`%xx` декодируется |

Дубликат известного поля или некорректная percent-последовательность отклоняются. Неизвестные поля игнорируются. Адрес проверяется на разрешённые символы, но синтаксис IPv4/имя DNS не проверяется глубже; IPv6-адрес с двоеточиями не проходит. После успешной проверки настройки записываются в NVS blob и только затем запускается подключение.

Постоянная конфигурация production хранится в NVS namespace `wifi_zabbix`, ключ `config`. На странице пароля сохранённой сети нет в подставленном HTML. При ошибке подключения AP остаётся доступной, пока станция повторяет попытки, чтобы оператор мог исправить профиль. После получения IP от домашнего роутера HTTP-сервер останавливается и режим меняется на STA, AP выключается.

### Обычная загрузка, PRG, RST и стирание

- **RST или обычный перезапуск/отключение и возврат питания:** код читает сохранённый namespace `wifi_zabbix` и запускает STA с сохранёнными настройками. Это поведение следует из исходников; физическое нажатие RST и power cycle в проверках не выполнялись.
- **PRG / GPIO0:** по исходникам, после обычного старта удержание кнопки около 5 секунд (задача опрашивает GPIO с периодом порядка 100 мс) запрашивает setup AP, отключает STA и позволяет сохранить новый профиль. Это не factory reset: само нажатие не очищает NVS. Физическое удержание кнопки на плате не проверялось.
- **Не держать PRG во время reset:** GPIO0 — strap pin, считываемый ROM при старте; удержание во время reset может вместо приложения включить ROM download mode.
- **Factory erase:** пользовательского пункта или кнопочной комбинации очистки NVS нет. Обычный RST/power cycle данные не стирает. `wifi_config_clear()` существует как функция кода, но production-поток её не вызывает; её используют тесты только в тестовом namespace. Не выполнять `erase-flash` и не очищать production NVS для обычной смены сети — используйте портал PRG.

### Состояния, reconnect и поля диагностики

В `wifi_state` используются `unconfigured`, `provisioning`, `connecting`, `online`, `retry_wait`, `error`. Обычное событие `WIFI_EVENT_STA_DISCONNECTED`, обработанное запущенной задачей менеджера, ставит следующую попытку с интервалами 1, 2, 4, 8, 16, 32 и максимум 60 секунд; успешное получение IP сбрасывает backoff. Дополнительные граничные случаи ниже выведены из исходников, а не подтверждены аппаратными испытаниями:

- **Первоначальный старт:** синхронная ошибка `esp_wifi_connect()` внутри `start_station_mode()` возвращается из `wifi_manager_start()` до создания `manager_task`. На этом пути deadline повтора не назначается, а manager task (включая опрос PRG) не запускается.
- **Обычный disconnect:** `WIFI_EVENT_STA_DISCONNECTED`, обработанный уже работающей `manager_task`, назначает bounded backoff: 1, 2, 4, 8, 16, 32 и максимум 60 секунд.
- **Timer retry:** после наступления `retry_at_us` задача вызывает `esp_wifi_connect()`. При `ESP_OK` код устанавливает `connecting`, но не очищает и не сдвигает уже истёкший `retry_at_us`; условие остаётся истинным, поэтому вызов может повторяться на последующих итерациях примерно через 100 мс, пока обработка события не очистит/переназначит deadline (например, получение IP или disconnect) либо очередной синхронный вызов не вернёт ошибку. При синхронной ошибке в этом retry-loop назначается следующий deadline с backoff.
- **Сохранение профиля:** обработчик события сохранения обнуляет deadline и вызывает `start_station_mode(true)`, но не проверяет его результат и не назначает отдельный retry deadline при немедленной ошибке `esp_wifi_connect()`. Последующий `WIFI_EVENT_STA_DISCONNECTED`, если он придёт, обрабатывается обычным disconnect-путём.

Отдельного watchdog/таймаута DHCP или состояния «нет IP» нет: одно лишь отсутствие IP не запускает retry; если станция остаётся ассоциированной, но IP не получен и disconnect-событие не приходит, менеджер может остаться в `connecting` без новой попытки. Периодические измерения продолжаются независимо от доступности Wi-Fi.

`wifi_error` — категория `none`, `no_ap`, `auth_failed`, `association_failed`, `handshake_timeout`, `beacon_lost`, `connection_failed`, `driver_error`, `configuration_error` или `other`. `wifi_reason_code` — числовой код disconnect из ESP-IDF. Основные коды, которые классифицирует менеджер:

| ESP-IDF reason | Число | Категория / обычная проверка |
|---|---:|---|
| `WIFI_REASON_NO_AP_FOUND` | 201 | `no_ap`: проверить 2,4 ГГц, SSID, сигнал и доступность точки |
| `WIFI_REASON_NO_AP_FOUND_W_COMPATIBLE_SECURITY` | 210 | `no_ap`: режим защиты точки не совместим |
| `WIFI_REASON_NO_AP_FOUND_IN_AUTHMODE_THRESHOLD` | 211 | `no_ap`: проверить режим аутентификации точки |
| `WIFI_REASON_NO_AP_FOUND_IN_RSSI_THRESHOLD` | 212 | `no_ap`: проверить сигнал/удалённость |
| `WIFI_REASON_AUTH_FAIL` | 202; `WIFI_REASON_AUTH_EXPIRE` 2; `WIFI_REASON_AUTH_LEAVE` 3; `WIFI_REASON_802_1X_AUTH_FAILED` 23; `WIFI_REASON_ASSOC_NOT_AUTHED` 9; `WIFI_REASON_BAD_CIPHER_OR_AKM` 29; `WIFI_REASON_GROUP_CIPHER_INVALID` 18; `WIFI_REASON_PAIRWISE_CIPHER_INVALID` 19 | `auth_failed`: проверить пароль и тип защиты Wi-Fi |
| `WIFI_REASON_ASSOC_FAIL` | 203; `WIFI_REASON_ASSOC_TOOMANY` 5 | `association_failed`: проверить ограничения/список клиентов точки |
| `WIFI_REASON_HANDSHAKE_TIMEOUT` | 204; `WIFI_REASON_4WAY_HANDSHAKE_TIMEOUT` 15; `WIFI_REASON_GROUP_KEY_UPDATE_TIMEOUT` 16 | `handshake_timeout`: проверить пароль, сигнал и совместимость WPA |
| `WIFI_REASON_BEACON_TIMEOUT` | 200 | `beacon_lost`: сигнал/перезагрузка точки/радиопомехи |
| `WIFI_REASON_CONNECTION_FAIL` | 205 | `connection_failed`: общий отказ соединения; проверить точку и повторить |

`WIFI_REASON_UNSPECIFIED` (1) — также отображается как `other`; это же значение используется как fallback, если event не передал reason. Другие коды ESP-IDF не приравниваются к отдельной категории и отображаются как `other`, но их исходное число остаётся в `wifi_reason_code`. Имена и номера взяты из `esp_wifi_types_generic.h` ESP-IDF 6.1.0.

## 7. Zabbix Sender: хост, элементы, расписание и ошибки

Прошивка устанавливает исходящее TCP-соединение к заданному адресу и порту (обычно 10051). Это протокол Zabbix Sender, не Zabbix Agent: пакет начинается `ZBXD\x01`, за ним следуют 8 байт little-endian длины и JSON. Входящее соединение на ESP для передачи метрик не требуется.

Имя узла в каждом пакете жёстко зашито: **`server-room-esp32`**. В Zabbix для него создать/включить три trapper-элемента:

| Имя | Key | Type | Тип значения | Единицы |
|---|---|---|---|---|
| Temperature | `sensor.temperature` | Zabbix trapper | Numeric (float) | `C` |
| Air pressure | `sensor.pressure_pa` | Zabbix trapper | Numeric (float) | `Pa` |
| Sensor status | `sensor.status` | Zabbix trapper | Character | — |

При валидном снимке пакет содержит все три элемента. При ошибке датчика он содержит только `sensor.status` со значением `error`; ноль и устаревшее число не подставляются. При восстановлении датчика отправляются свежие числовые значения и `ok`.

Отправитель проверяет состояние Wi-Fi примерно каждые 250 мс. При переходе в `online` планирует первую отправку сразу (если снимок уже доступен), затем следующую через 10 секунд. Если снимка ещё нет, этот цикл не отправляет данные; следующий цикл наступает по расписанию. При offline sender показывает `waiting`, не создаёт историю очереди; при reconnect начинает отправку последнего снимка.

Статусы `zabbix_send_state`: `waiting`, `ok`, `error`. `zabbix_stage` показывает место сбоя:

| Stage | Значение / причина | Действие оператора |
|---|---|---|
| `none` | Ошибки этапа нет; также нормальное ожидание без Wi-Fi | Сопоставить со `zabbix_send_state` и `wifi_state` |
| `config` | Не удалось загрузить/проверить адрес, порт или конфигурацию | Повторно сохранить адрес/порт через setup portal; проверить NVS-ошибку в логе |
| `build` | Не удалось построить JSON/frame (неверный аргумент/размер) | Сверить firmware build и данные датчика; это не сетевой firewall-сбой |
| `resolve` | DNS/разрешение имени не найдено; обычно `ESP_ERR_NOT_FOUND` | Проверить написание имени, DNS и доступность LAN; временно указать LAN IPv4 сервера |
| `connect` | TCP-соединение не открыто (`ESP_FAIL` или `ESP_ERR_TIMEOUT`) | Проверить IP Windows-ПК, порт 10051, Docker port binding, клиентскую изоляцию роутера и точечное правило firewall |
| `send` | Не удалось передать TCP-кадр; возможен таймаут/обрыв | Проверить маршрут, firewall и журнал Zabbix server; повтор произойдёт по расписанию |
| `response_header` | Нет полного заголовка за таймаут, peer закрыл соединение или неверна сигнатура/длина | Убедиться, что на выбранном IP:port отвечает именно Zabbix Server trapper, а не веб-порт/другой сервис |
| `response_body` | Заголовок получен, но тело ответа не пришло полностью | Проверить серверный ответ/сетевой обрыв |
| `validate` | Ответ не содержит ожидаемых `"response":"success"` и `failed: 0` | Проверить trapper, host/key/Allowed hosts и фактический ответ сервера |

Для каждого вызова `select()` ожидание готовности сокета ограничено 3 секундами. `send_all()` и `receive_all()` могут повторять эти ожидания при частичном I/O; при нескольких адресах, возвращённых DNS, прошивка может последовательно сделать несколько отдельных timed connect попыток. `getaddrinfo()` вызывается синхронно и не имеет заданного в проекте таймаута. Поэтому 3 секунды — лимит отдельного ожидания `select()`, а не общий deadline отправки пакета или batch. `ESP_ERR_TIMEOUT` (0x107) означает, что одно такое ожидание истекло; на `connect` проверить доступность listener/маршрут, на `response_header`/`response_body` — почему peer не ответил вовремя. Поле `zabbix_error` выводит `esp_err_to_name()` последнего результата; успешный пакет даёт `zabbix_stage=none` и `zabbix_error=ESP_OK`.

### Часто встречающиеся ESP error имена

Код ошибки зависит от этапа; ниже перечислены коды, которые используются или могут возвращаться проверяемыми функциями проекта, а не исчерпывающий каталог ESP-IDF.

| Имя | Значение | Где проявляется / что проверить |
|---|---:|---|
| `ESP_OK` | 0 | Операция завершилась без ошибки |
| `ESP_ERR_NO_MEM` | 0x101 | Не выделена память/не создана задача или объект; перезапустить, проверить heap и повторяемость |
| `ESP_ERR_INVALID_ARG` | 0x102 | Некорректная форма, адрес, порт, аргумент драйвера; проверить поля ввода/вызова |
| `ESP_ERR_INVALID_STATE` | 0x103 | Повторный старт, неверный формат сохранённого blob или некорректное состояние; проверить логи, не стирать NVS автоматически |
| `ESP_ERR_INVALID_SIZE` | 0x104 | Размер буфера или ответного кадра недопустим; stage `build` или `response_header` |
| `ESP_ERR_NOT_FOUND` | 0x105 | Ключа конфигурации/снимка нет или адрес не разрешился; смотреть stage и `wifi_state` |
| `ESP_ERR_NOT_SUPPORTED` | 0x106 | ID датчика не 0x58 (BMP280) |
| `ESP_ERR_TIMEOUT` | 0x107 | BMP280 не вышел из busy либо timeout TCP connect/send/receive; учитывать stage |
| `ESP_ERR_INVALID_RESPONSE` | 0x108 | Недостоверный raw/компенсация датчика, неожиданный ответ или неверная sender-сигнатура |
| `ESP_FAIL` | −1 | Общий отказ socket/API; смотреть stage и системные логи |
| `ESP_ERR_NVS_NOT_FOUND` | NVS-код | В namespace/key нет конфигурации; штатный случай первой настройки — запускается AP |
| `ESP_ERR_NVS_NO_FREE_PAGES` | 0x110D | NVS не имеет свободных страниц; менеджер не стирает NVS автоматически, сохранённые настройки не очищать без отдельного плана восстановления |
| `ESP_ERR_NVS_NEW_VERSION_FOUND` | 0x1110 | Формат NVS новее, чем поддерживает эта прошивка; не стирать partition как первый шаг |
| `ESP_ERR_WIFI_NOT_INIT` | 0x3001 | Вызов Wi-Fi API до инициализации драйвера; проверить порядок инициализации |
| `ESP_ERR_WIFI_NOT_STARTED` | 0x3002 | Wi-Fi driver ещё не стартовал; проверить результат `esp_wifi_start()` |
| `ESP_ERR_WIFI_STATE` | 0x3006 | Операция несовместима с текущим состоянием Wi-Fi |
| `ESP_ERR_WIFI_CONN` | 0x3007 | Менеджер записывает при disconnect; подробная причина отдельно в числовом `wifi_reason_code` |

Если setup form не проходит parser/валидацию, HTTP отвечает 400. Ошибка выделения памяти для тела формы отвечает 500. Ошибка сохранения конфигурации сейчас также попадает в ветку общего ответа 400; проверить корректность формы и USB/ESP log, не повторять беспорядочно destructive-команды. Ошибки старта HTTP/Wi-Fi/NVS могут быть видны в ESP log; USB JSON содержит итоговые поля статуса, но не все причины внутренней инициализации.

## 8. Безопасность и эксплуатационные ограничения

- Setup AP защищён WPA2 случайным временным паролем, но страница использует обычный HTTP на локальном AP. Пароль Wi-Fi передаётся по HTTP внутри этой радиосети; используйте setup только рядом с доверенным операторским устройством и отключитесь после настройки.
- Временный пароль setup AP виден на OLED всё время активного setup режима и передаётся отдельным USB-сообщением при запуске AP. Не публиковать фото дисплея, serial log или скриншоты настройки.
- Информационные Wi-Fi логи ESP-IDF могут содержать SSID подключённой сети (это наблюдалось в monitor). Периодический JSON приложения SSID/пароль не включает, но raw setup/boot logs могут содержать SSID, временный setup пароль и другие диагностические сведения. Перед передачей логов наружу редактировать чувствительные строки целиком.
- Домашний SSID/пароль и адрес/порт сервера сохраняются в NVS namespace `wifi_zabbix`, ключ `config`; периодические JSON их не выводят. В активном `sdkconfig` отключены `CONFIG_NVS_ENCRYPTION` и `CONFIG_FLASH_ENCRYPTION_ENABLED`. При физическом доступе к Flash секреты не защищены шифрованием на устройстве.
- TCP sender plaintext, TLS/PSK в этой прошивке не реализованы. Ограничивать доступ к TCP 10051 на стороне Zabbix (`Allowed hosts`) и Windows firewall до конкретного стабильного IP платы/частной LAN; не открывать порт всему Интернету или всем профилям.
- Zabbix Server принимает исходящие данные от ESP32; приложение не отправляет уведомления само, не делает backfill, не хранит очередь истории и не контролирует отключение питания узла. Триггеры/уведомления настраиваются отдельно в Zabbix.
- Отчёт sender `ok` — проверка ответа протокола прошивкой, а не проверка UI или ручной валидации истории.

## 9. Unity и Python serial проверки

### Unity: Wi-Fi/Zabbix test firmware

В `main/CMakeLists.txt` временно выбрать `wifi_zabbix_test.c`, собрать и загрузить именно test firmware. При такой сборке к `wifi_config.c` добавляется `WIFI_CONFIG_TEST_NAMESPACE`; тесты используют namespace **`wifi_zx_test`**, production namespace остаётся `wifi_zabbix`. Не выбирать/стирать production NVS ради теста. Тестовая прошивка стартует отдельный тестовый AP и локального TCP peer, не передаёт метрики в рабочий Zabbix и не заменяет production-прошивку в эксплуатации. После теста вернуть `temperature_monitor.c`, пересобрать и загрузить production firmware.

В ранее выполненном запуске **28 Unity-тестов прошли**. Они проверяют:

1. Валидность конфигурации и отклонение пустого SSID, пустого адреса Zabbix и нулевого порта.
2. Отсутствие конфигурации в NVS и сохранение/чтение валидной конфигурации с очисткой только тестового ключа.
3. Разбор form-urlencoded: `+`, `%xx`, порт по умолчанию; отказ при отсутствии сервера, неправильном порте и malformed escape.
4. Старт/останов HTTP provisioning server.
5. Переходы автомата Wi-Fi: provisioning, connecting→online, online→retry, PRG→provisioning, error; разбор коалесцированных connected/disconnected событий.
6. Безопасную классификацию auth-fail и no-AP reason.
7. Сборку Zabbix Sender frame с сигнатурой `ZBXD\x01`, little-endian длиной и проверку недостаточного буфера.
8. Правильные имена stages, валидный payload с тремя ключами и ошибочный payload только со статусом.
9. Три теста с локальным TCP peer: успешный фрагментированный ответ, неправильная сигнатура заголовка и таймаут ожидания response header.

Wi-Fi state/reason тесты вызывают только pure helpers `wifi_manager_transition()`, `wifi_manager_resolve_station_events()` и `wifi_manager_classify_disconnect_reason()`. Они не запускают `manager_task`, не измеряют время удержания GPIO и не выполняют реальный reconnect loop/backoff. Поэтому 28 Unity-тестов не являются аппаратной проверкой PRG, RST или восстановления связи.

Итог тестовой прошивки печатает `UNITY_DONE tests=28 failures=0`. Результаты этих peer-тестов не доказывают доставку реальных метрик в Zabbix production.

Перед каждым запуском закрыть `idf.py monitor` (Ctrl+`], затем дождаться закрытия COM-порта). Запускать из корня проекта, из ESP-IDF PowerShell окружения, указывая обнаруженный номер COM-порта вместо примера:

| Команда | Требуемая прошивка | Что проверяет |

После перевода пользователем сетевого интерфейса 10 в профиль **Private** свежие production serial-отчёты неоднократно показывали `wifi_state=online`, `zabbix_send_state=ok`, `zabbix_stage=none`, `zabbix_error=ESP_OK`. Запуск `python tools/check_zabbix_firmware.py COM4` прошёл. Во время monitor-triggered USB reset прошивка повторно загрузила сохранённые настройки, получила адрес `192.168.0.2` и примерно за 3 секунды достигла online/sender-ok. Это наблюдение после USB reset не является проверкой физической кнопки RST или отдельного power cycle.

## 10. Развёртывание на чистой Windows-машине: ESP-IDF и прошивка

### 10.1 Подготовить Windows и исходники

1. Установить драйвер USB платы, VS Code и расширение Espressif ESP-IDF либо штатный набор ESP-IDF Tools. Установить **ESP-IDF 6.1.0**, включая Python environment, Xtensa toolchain, CMake и Ninja для ESP32-S3.
2. Клонировать [репозиторий Oled1](https://github.com/fortarkovomenxiii/Oled1) можно только после публикации release/revision, содержащей именно требуемые текущие исходники и документы. Рабочая версия, описанная этой запиской, включает локальные uncommitted/untracked изменения и может отсутствовать в опубликованном GitHub-состоянии. **Пока такая revision не опубликована, перенести на новый ПК точный проверенный snapshot рабочей папки** согласованным способом; открыть в VS Code его корень, где находятся `CMakeLists.txt`, `sdkconfig.defaults`, `dependencies.lock` и `main/`. Для планируемого private snapshot исключить `build/`, `.vscode/`, credentials, локальные secret-файлы и резервные копии с данными.

   ```powershell
   Set-Location "<путь-к-перенесённому-снимку-Oled1>"
   ```
3. Каталог `.vscode/` не включать в private snapshot: его `settings.json` и `tasks.json` содержат локальные абсолютные пути `D:\Espressif\...`, `Activate-Oled1.ps1` и COM4. На другом ПК локально установить/настроить ESP-IDF extension, выбрать установленную версию через **ESP-IDF: Select Current ESP-IDF Version** и указать обнаруженный COM-порт; не переносить настройки и терминальный профиль текущей машины вслепую. Команды в `START_HERE_RU.md`, включая команды с COM4 и локальными путями, являются примерами для этого ПК и требуют адаптации.
4. В Device Manager → **Ports (COM & LPT)** найти COM платы после подключения data-кабелем. Для текущего компьютера исторически указан COM4; на новой машине номер определить заново. Закрывать монитор перед прошивкой и Python-тестом.

### 10.2 Сборка и загрузка production

В ESP-IDF PowerShell терминале из корня проекта проверить селектор в `main/CMakeLists.txt` — `temperature_monitor.c`, затем:

```powershell
idf.py --version
idf.py set-target esp32s3
idf.py build

```

Ожидается ESP-IDF v6.1.0, target ESP32-S3; Component Manager загрузит зафиксированный OLED компонент. `COMx` заменить на порт из Device Manager. `flash` загружает выбранные образы проекта; это не команда factory erase. **Не запускать `idf.py erase-flash`, `nvs_flash_erase` и не выполнять очистку production namespace.** Для выхода из monitor — Ctrl+`]`. На старте при пустом профиле открыть SSID setup AP на телефоне/ноутбуке, ввести временный AP пароль с OLED/однократного USB сообщения, вручную открыть `http://192.168.4.1`, указать свою домашнюю сеть 2,4 ГГц, LAN IPv4/hostname Windows Zabbix Server и порт (обычно 10051), сохранить и наблюдать состояние на OLED/USB.

Если тесты нужны, сначала зафиксировать/подтвердить использование устройства, переключить selector на требуемый test firmware, собрать/загрузить его и после теста вернуть production selector и firmware. Для обычного ввода в эксплуатацию тестовая прошивка не требуется.

Убедиться, что Docker CLI использует контекст работающего Docker Desktop (`docker context show`; обычно контекст называется `desktop-linux`), и проверить `docker compose version` (не ниже 2.24.0) и наличие GNU Make (`make --version`). На Windows удобнее выполнять цели Make из Git Bash или WSL с интеграцией Docker Desktop; PowerShell также подходит, если GNU Make настроен на совместимую POSIX-оболочку для рецептов Makefile. Обеспечить стабильное LAN-подключение ПК.
2. Получить официальную ветку и подготовить локальное окружение по README. В PowerShell:

   ```powershell
   git clone --branch 7.4 --depth 1 https://github.com/zabbix/zabbix-docker.git
   Set-Location .\zabbix-docker
   # До первого постоянного запуска локально просмотреть .env/env_vars и задать уникальные DB credentials.
   docker context show
   docker compose version
   make --version
   make up CONTAINER=docker OS=alpine
   docker compose ps
   ```

   В PowerShell запускайте эту последовательность, только если GNU Make настроен на совместимую POSIX-оболочку для рецептов Makefile; иначе используйте Git Bash или WSL с интеграцией Docker Desktop. Эквивалентные команды в Git Bash/WSL после подготовки локального окружения:

   ```bash
   cd zabbix-docker
   docker context show
   docker compose version
   make --version
   make up CONTAINER=docker OS=alpine
   docker compose ps
   ```

   `CONTAINER=docker` явно выбирает Docker (Makefile иначе автоматически предпочитает Docker при наличии, затем Podman); проверить, что `docker context show` указывает на работающий Linux engine Docker Desktop (обычно `desktop-linux`). `OS=alpine` следует указывать явно в Windows-среде: переменная окружения Windows `OS` может иметь значение `Windows_NT` и перекрыть Makefile-значение по умолчанию; `OS` выбирает базовый образ, а не Docker engine. `make up` использует remote images, поэтому Buildx нужен только для отдельного локального build/up-local сценария. Если Compose сообщает об отсутствующих переменных или файлах, проверить полноту checkout и локальные overrides, затем свериться с README/Makefile этой ветки; штатные `.env` и файлы/шаблоны `env_vars/` входят в официальный репозиторий. DB/admin credentials настроить локально и не публиковать; не вставлять их в issue, чат, документацию или общий log и не отключать Compose secrets для обхода ошибки. После запуска `docker compose ps` должен показать состояние сервисов MySQL, Zabbix Server и Web frontend; первая инициализация БД может занять время.
3. Получить IPv4-адрес LAN-интерфейса Windows-ПК командой `ipconfig`; не указывать ESP адрес `127.0.0.1`, Docker bridge IP или адрес Wi-Fi AP настройки устройства. Зарезервировать постоянный адрес платы в DHCP роутера после подключения. На роутере проверить, что Wi-Fi client/AP isolation не мешает станции обращаться к Windows-ПК.
4. Открыть Zabbix frontend по опубликованному web-порту Windows-ПК (сверить порт в `docker compose ps`; для стандартного nginx frontend путь обычно `/`, для Apache официальный quickstart указывает `/zabbix`). Для новой, только что установленной официальной Zabbix-системы quickstart документирует первоначальный логин `Admin` и пароль `zabbix`; **немедленно сменить пароль Admin после первого входа**. Это учётная запись веб-интерфейса Zabbix, не MySQL/Docker DB secrets. На уже существующем ПК использовать его уже настроенную Zabbix учётную запись и пароль, не предполагать, что там действует первоначальный default. См. [официальный Zabbix 7.4 quickstart: Login and configuring user](https://www.zabbix.com/documentation/7.4/en/manual/quickstart/login). После входа создать/проверить host с точным technical host name `server-room-esp32`, включить его и добавить trapper items из таблицы выше с совпадающими key/value type/unit. В item **Allowed hosts** ограничить отправку стабильным IP платы (или минимальным нужным доверенным сегментом), а не `0.0.0.0/0`. Время обновления задаётся sender прошивки; у trapper items polling interval не используется как команда опроса ESP.
5. Windows Firewall: сначала убедиться, что сеть является доверенной LAN (`Get-NetConnectionProfile`). Если доверенный интерфейс ошибочно помечен `Public`, из elevated PowerShell перевести только его по `InterfaceIndex` в `Private`; не менять профиль неизвестной/публичной сети:

   ```powershell
   Get-NetConnectionProfile
   Set-NetConnectionProfile -InterfaceIndex <LAN-InterfaceIndex> -NetworkCategory Private
   ```

   После этого проверить доступность TCP local port 10051. Только если sender показывает `stage=connect`/timeout и порт блокируется, из elevated PowerShell добавить узкое входящее правило с фактическими адресами ПК и DHCP-reserved ESP32:

   ```powershell
   $zabbixIp = "<LAN-IP-PC>"
   $espIp = "<DHCP-reserved-IP-ESP32>"
   New-NetFirewallRule -DisplayName "Zabbix Sender from ESP32" `
     -Direction Inbound -Action Allow -Protocol TCP -LocalPort 10051 `
     -LocalAddress $zabbixIp -RemoteAddress $espIp -Profile Private
   ```

   Сеть переводить в Private можно только если это доверенная LAN; проверить её интерфейс командой `Get-NetConnectionProfile`. Не создавать широкое правило на `Any`, не открывать Public/Domain профили и не отключать firewall. `Allowed hosts` у trapper items ограничить тем же reserved IP. Сверить фактический Docker published port: у текущей установки наблюдалось `0.0.0.0:10051` (все IPv4 интерфейсы). Если требуется сузить listener до LAN IP, менять локальный Compose override/config только по документации установленной версии и после проверки `docker compose ps`.
6. В Wi-Fi setup форме устройства указать LAN IPv4/hostname Windows-ПК и TCP 10051. Убедиться в USB отчёте, что `wifi_state=online`, а после отправки `zabbix_send_state=ok`, `zabbix_stage=none`, `zabbix_error=ESP_OK`.
7. Вручную открыть **Monitoring → Latest data**, выбрать `server-room-esp32`, найти три ключа и дождаться новых значений (sender интервал порядка 10 секунд). На момент этой записи Latest data остаётся не просмотренным; UI-проверку должен выполнить оператор. Сверить значения, время последнего обновления и `sensor.status`.

На текущем Docker-хосте наблюдался server image **Zabbix 7.4.16**, port mapping `0.0.0.0:10051`; после изменения пользователем сетевого профиля Windows текущий LAN-профиль был **Private**. Отдельное firewall-правило для ESP32 не добавлялось. Ветка Docker `7.4` развивается: её текущий `latest` со временем может указывать на более новую patch-версию, поэтому для побитово воспроизводимого нового развёртывания сверить фактически выбранные теги образов в локальной конфигурации и явно закрепить нужный patch-релиз по официальной документации.

## 12. Диагностика по симптомам

| Симптом | Разбор и безопасное действие |
|---|---|
| При загрузке появляется setup AP | Сохранённая конфигурация отсутствует или недействительна. Настроить заново через форму; не очищать Flash |
| AP отсутствует, приложение не доходит до setup | Проверить USB/ESP log на инициализацию NVS, netif, event loop, Wi-Fi и `ESP_ERROR_CHECK`; ошибка `nvs_flash_init()` останавливает менеджер Wi-Fi, но основной цикл датчика может продолжаться |
| `wifi_state=retry_wait`, `wifi_error=no_ap` | Убедиться, что сеть 2,4 ГГц доступна, SSID точно введён, точка не скрыта/не изолирована; смотреть числовой `wifi_reason_code` |
| `auth_failed` / `handshake_timeout` | Исправить сохранённый пароль и режим защиты через PRG setup; проверить, что AP принимает WPA2-профиль |
| `wifi_state=online`, но sender stage `resolve` | Исправить server host/IP в форме, проверить локальный DNS; для диагностики использовать текущий LAN IPv4 сервера |
| Stage `connect`, `ESP_ERR_TIMEOUT` или `ESP_FAIL` | Проверить IP ПК, порт 10051, Docker `published` binding и service health, DHCP reservation, client isolation и узко заданное firewall scope |
| Stage `response_header` / `response_body` | TCP установился, но peer не дал протокольный ответ вовремя/закрыл соединение. Убедиться, что адрес ведёт к Zabbix Server trapper, а не к веб-интерфейсу |
| Stage `validate` | Ответ не прошёл проверку Sender response; сверить host/items, Allowed hosts, серверные логи и полученный ответ |
| `sensor.status=error`, raw данные присутствуют | Проверить raw-коды/диапазоны и адрес/модель датчика; проверить проводку и питание только после отключения питания |
| `raw_*` равны null или ошибка I2C на старте | Проверить GPIO4/6, 0x76, GND/3V3, CSB/SDO и подтяжки. Если ошибка была при создании шины/устройства, прошивка сама её не переинициализирует — после исправления аппаратуры нужен обычный reset |
| Sender `ok`, но в UI нет ожидаемых значений | Протокольное принятие не подтверждает ручную проверку UI; проверить точное technical host name, ключи, включённость items, Allowed hosts и время последних значений в Latest data |

## 14. Проверено и не проверено

### Подтверждено

- **Unity:** 28 тестов прошли, включая локальный TCP peer: принят успешный фрагментированный ответ, отклонён некорректный header, зафиксирован timeout response header.
- **Serial измерения:** проверки cadence около 1 секунды, raw полей и температуры/компенсации прошли согласно имеющейся записи.
- **Текущая сеть:** после перевода пользователем интерфейса 10 в Private свежие production serial-отчёты неоднократно показывали `wifi_state=online`, `zabbix_send_state=ok`, `zabbix_stage=none`, `zabbix_error=ESP_OK`; `python tools/check_zabbix_firmware.py COM4` прошёл.
- **Перезапуск по USB:** monitor-triggered USB reset перечитал сохранённые настройки, получил `192.168.0.2` и примерно через 3 секунды вернулся в online/sender-ok. Физические RST и power cycle этим не проверялись.
- **Zabbix Docker на проверенной машине:** наблюдались image Zabbix 7.4.16 и публикация TCP 10051 на `0.0.0.0`; Windows-профиль сети после изменения — Private. Новое специальное firewall-правило не создавалось.

Эти sender-success наблюдения — подтверждение принятого прошивкой протокольного ответа, не доказательство ручного просмотра Latest data.

### Следует из исходников, но аппаратно не проверено

- Удержание PRG/GPIO0 около 5 секунд после старта запрашивает setup AP; эта кнопка сама по себе NVS не стирает.
- Обычный RST/power cycle загружает сохранённый production профиль из NVS.
- Нормально обработанный `WIFI_EVENT_STA_DISCONNECTED` назначает bounded backoff; это не гарантия одинакового retry для всех путей — см. описанные выше startup, timer-retry и profile-save caveats.
- Успешное получение IP выключает setup AP и переводит радио из APSTA в STA; отправитель затем может отправить последний снимок.

### Не выполнялось / не заявляется

- Физическое удержание PRG 5 секунд.
- Физическое нажатие кнопки RST и отдельное отключение/возврат питания.
- Намеренная потеря Wi-Fi и наблюдение полного цикла recovery на плате.
- Ручное открытие Zabbix **Monitoring → Latest data** в ходе описанной проверки.

### Уточнения по источникам

- `main/idf_component.yml` заявляет IDF `>=4.1.0`, тогда как фактический `dependencies.lock` фиксирует 6.1.0, и OLED-компонент требует не ниже 5.3; для новой сборки использовать 6.1.0.
- Datasheet Heltec для соседней ревизии V4.3.1 называет встроенный дисплей SSD1315; код использует SSD1306-совместимый API. Точный контроллер панели на маркировке V4.3 этой запиской отдельно не переидентифицировался.
- `wifi_error` — категория классификатора manager, `wifi_reason_code` — числовой reason ESP-IDF, а `zabbix_error` — имя `esp_err_t`; эти поля не взаимозаменяемы.
- Документы `START_HERE_RU.md` и `PROJECT_AUDIT_RU.md` содержат более ранние/исторические статусы. Для актуальной сети использовать явно датированные/описанные здесь наблюдения, а не старое значение `ESP_ERR_TIMEOUT`.

Источник актуальных технических фактов — код выбранной `temperature_monitor.c` и связанных модулей, `sdkconfig`/lock и тесты. Исторические сетевые сообщения в `START_HERE_RU.md` могли быть зафиксированы до перевода Windows сети в Private; они не должны подменять более поздние наблюдения, перечисленные выше.
